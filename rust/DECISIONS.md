# Decisions

All ADRs below were taken by the agent, using the recommended answer. The user approved the port as a whole
("download rust-anything and port everything worthwhile, and the sensible parts"); no interview took place.
Status for every ADR: accepted (2026-11-27).

## ADR-001: Scope
Context: the repo is a ±2500-line bash manager (`ark-manager.sh`), a 157-line Python RCON client (`rcon.py`), install/health scripts
and a Node/Express dashboard (backend ±2000 lines JS, a bundled React frontend).
Decision: port (1) the dashboard backend to Rust (axum) and (2) the pure parts of the manager and RCON client to a clap CLI.
Out of scope, kept as is: the frontend (`dashboard/frontend`, UI + vendor bundles), `install.sh`, `healthcheck.sh`, everything that
executes docker/qm/systemctl/ssh/proton. Source says: decided by agent, recommended answer.
Consequences: the Rust backend serves the existing frontend unchanged (it reads the files from disk).

## ADR-002: Server shape
Decision: axum with one fallback handler that routes by hand (`rust/dash/src/server.rs::dispatch`). Express behaviour that matters is
reproduced: auth before everything, `express.json()` on every request, case-insensitive routes with optional trailing slash,
static folder then SPA fallback then the default 404 page.
Consequences: no per-route axum extractors; parity is proven by replay, not by types.

## ADR-003: Execution behind a trait; what is not ported
Decision: `Exec` trait (`guest_shell`, `guest_exec`, `vm_status`, `rrddata`, `vm_power`). Implementations: `LocalExec` (sudo -u, port of
`local.js`, compiled and unit-tested for its argv, never run in this work) and `FakeVm` (in-memory, port of the harness fake).
`proxmox.js` (guest-agent over the PVE API) and `unifi.js` (WAN port-forward) are NOT ported: the Rust server refuses to start when
`ARK_EXEC_MODE=proxmox` or the UniFi variables are set, instead of silently ignoring them.
Consequences: the Rust backend cannot replace the Node backend on CT120 (which talks to VM1050 through Proxmox) until `proxmox.js`
is ported. VM1050 and every other host were never contacted.

## ADR-004: Recording the original offline
Decision: `rust/harness/run-original.js` starts the real `dashboard/backend/server.js` with `local.js` replaced (via `require.cache`)
by `fake-vm.js`, an in-memory VM answering the exact shell scripts the backend sends. No process is spawned, no sudo, no network.
Credentials are dummies (`admin` / `dummy-dash-pass`, `dummy-admin-N`). `POLL_INTERVAL_MS=600000` so only the start-up poll runs
(the poller is time-driven and would otherwise make state depend on timing); the listener opens 700 ms after start so that poll is done.
Consequences: recorded behaviour is the backend's behaviour against a synthetic VM, not against a real manager.

## ADR-005: Equivalence bar
Decision: status code, content-type, the headers `app record` keeps (auth challenge, cache-control, location, CSP) and the body must match;
the original's own noise (timestamps) became `[..]` wildcards. Not reproduced on purpose: Express' development error pages with a
stack trace (malformed JSON bodies, undecodable `%` in a path): the Rust server answers 400 with the same page layout and the error
message but no stack. Those cases were left out of the recording because their bodies contain the machine's file paths.
Not reproduced: `Last-Modified`/`ETag`, range requests, HEAD bodies (HEAD is routed like GET, with no body), Express' prototype-key
quirks (`/api/instance/constructor`).

## ADR-006: The server is ported as one piece, not route by route
Context: routes share state (instance cache, audit log, poller, per-instance caches). A route answered in Rust while the rest is
proxied to the original would read a different state.
Decision: `rust/dash` implements every route; `rust/app` (the generated front door, 100% fallback) stays as the recorded baseline and is
not wired. `app wire`/`app lift` are therefore not used. The proof is `app replay --build "sh rust/dash/run-fake.sh"`.

## ADR-007: Pure manager parts as a library + clap CLI
Decision: `rust/ark-ctl`: `conf` (read/write conf values), `rcon` (packets, handshake, command loop, player count over a `Transport`),
`launch` (launch plan, mod ids, pgrep pattern, GameUserSettings password rewrite), `unit` (systemd unit), `plan` (add-map options and the
files it would write), `system` (`System` trait + `FakeSystem` for anything that would execute). The CLI only prints plans; there is no
command that starts, stops or reconfigures anything.
Proof: differential tests run the manager's own `read_conf_value`/`write_conf_value` in bash and `rcon.py` (vectors generated by
`scripts/gen-vectors.py` with a fake socket) against the Rust functions.

## ADR-008: Only `suggestPorts` goes through the unit pipeline
Context: `ark.js` exports `ArkInstance` (class, kept in JS), and three async functions that take the executor object.
Decision: bridge `ark.js` with `--keep` for those three; `rust/ark-rs` ports `suggestPorts` (bridge, record, diff 31/31, gate passed).
Everything else of `ark.js` is ported by hand in `rust/dash/src/ark.rs`, covered by replay.

## ADR-009: Deliberate differences
- `.env` files are not loaded (the Node backend calls `dotenv`); export the variables, or use systemd `EnvironmentFile=`.
- `ark-ctl add-map` with an option that lacks its value is an error; the shell script loops forever on it.
- `ARK_EXEC_MODE=fake` exists only in the Rust server (and `run-fake.sh`) for replay and tests.
- Date handling of the `ExecMainStartTimestamp` treats every time zone abbreviation as UTC.
